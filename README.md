# astrbot_plugin_qiniu_image

七牛 Modelink 绘图 / 改图插件，适用于 AstrBot。当前版本 **2.2.4**。绘图与关键词基础仍来自 **1.3.0（`5020e13`）**，不使用之后的外观定字段、角色缓存和复杂人物任务结构。

## 模型分工

| 模型 | 职责 |
| --- | --- |
| 主聊天模型 | 解释用户意图、会话指代和必要人设，给出硬性要求与创作自由度，检查摘要并决定出图 |
| 绘图规划模型 | 在独立上下文里搜索、核对特征，从内置目录选风格再设计动作与构图，准备完整方案 |
| 提示词模型 | 沿用已审核风格，只选择相容的既有片段与全局兜底，保留核心风格，完整方案逐字保留 |
| 图片模型 | 执行已确认方案并生成图片 |

主聊天模型不需要承担整套搜索/核对流程，也不默认接收长提示词、网页内容或图片核对过程。规划模型只接收本次委托、按需读取的历史提示词，以及用户输入图片，不读取完整聊天历史。

## 使用流程与主模型控制

1. 主模型调用 `prepare_drawing(brief)`。委托应写清意图、必要人设/指代、硬性要求和允许自由设计的部分。例如“你的自拍”必须先说明“你”的形象，不能让规划模型猜群聊上下文。
2. 插件返回方案编号、简短摘要、搜索次数及各主体核对状态，尚不出图。
3. 主模型检查摘要。不满意时调用 `prepare_drawing(brief="具体修改要求", base_plan_id="原编号")`，新方案准备成功后旧的待审稿失效；符合委托后调用 `draw_image(plan_id, caption="按当前人格写的短回复")`。
4. 插件立即返回 `accepted` 与编号，后台整合风格、保存完整提示词，然后生成并发图。同一方案不能重复执行；模型回退耗时不再占用 `draw_image` 的工具超时。

规划搜索最多等待40秒。超时、核对记录无效或规划模型不可用时，停止当前搜索与核对，再用已有资料进行一次最多10秒的无工具收尾；收尾仍不可用则直接使用委托、原基稿和已确认特征。该兜底路径自动提交出图，`prepare_drawing` 直接返回 `accepted` 和 `degraded=true`，主模型不要重新准备或重复提交。同一消息内重复提交相同兜底委托会返回原编号；新的绘图消息仍分别处理。

普通方案的提示词整合最多等待20秒，失败或超时后在本地保留完整方案并追加已选画风的核心片段和基础质量要求。规划已经降级时直接走本地整合，不再等待整合模型。这里的时限只约束前置步骤，实际图片生成仍需等待七牛返回。

函数绘图的 auto 在规划阶段确定风格方向，不再先生成3D、厚涂或极高细节方案，再让整合器以“不相容”为由放弃预设。规划模型在同一次调用里读取完整目录、选择相容风格并设计画面，不增加一次模型请求。整合器不能改选或跳过已审核风格，也不能删掉核心视觉片段、只保留“干净壁纸”和横向比例。

自动偏好：单人/单主体优先错位矩形、诗意窗口等，净色动画壁纸为低优先；多人/多主体时净色动画壁纸为高优先。配饰、衣服和普通背景不单独算主体。明确指定与相容性优先于这些偏好，单人仍可点名净色动画壁纸，不随机强套某一风格。

`prepare_drawing(..., style_request="用户明确说出的画风原话")` 单独传递用户风格要求；只说“画某角色”时留空，不能把该角色原作的3D/厚涂媒介当成用户要求。修改内容时留空沿用旧风格，换风格时填写新要求，恢复自动选择填 `auto`。`disabled`、`explicit_only` 和局部改图的原有规则仍适用。

绘图过程静默执行，主模型不播报“正在规划、核对完成、重试、后台加速”等过程话术。短回复通常由主聊天模型按当前人格提供，简单说画谁即可，例如“这次画元气千束喵～”；自动兜底时使用“按你的要求画一张。”。插件等完整提示词实际准备好后代发这一句，再发送成图。失败则简短报告失败，不把受理或超时误说成已经开始出图。两个 Bot 同群可以各自正常响应，不做跨 Bot 去重。

连续请求分别处理；上一份仍待审核提交时，`prepare_drawing` 返回 `pending_review` 和旧方案摘要，主模型应先检查并提交，再继续新增请求。用户明确取消时使用 `cancel_drawing(plan_id)`；新增请求本身不表示取消。全部处理完后主模型输出非空内部标记 `QINIU_DRAWING_DONE`，由绘图事件的结果过滤隐藏，避免要求空回复与 Provider 的非空要求冲突。模型自身或服务返回空内容仍可能触发 AstrBot 的重试。

审核是主聊天模型的内部步骤，无需额外向用户索取批准。规划模型只获得联网和内部核对工具，没有出图、发送消息或修改文件的工具。方案编号保证出图使用已准备的那一稿，不能直接传自由提示词绕过规划。

主模型需要核查细节时，调用 `get_drawing_plan(plan_id, full=true)` 获取完整方案和实际搜索/核对依据；默认只给摘要。主模型对委托目标与执行决定有控制权，摘要是否充分、规划判断是否正确仍依赖模型能力。

## 规划模型的文生图流程

- 逐个主体判断：是否理解用户在说什么；是否有把握描述特征。任一没把握就先消歧、再搜特征，保留搜索前的原有认识。
- 文字特征一致就采用，不取图；无先验知识时，以明确可靠的搜索资料补足，不编造自己的认识。原创主体以委托设定为准。
- 只有文字特征冲突时，内部调用 `compare_subject_reference` 下载图片。图片是高优先级证据，只采用至少两方一致的共同特征。
- 第一轮无共识时重新搜索并取新图片，再核对一次；第二轮仍失败就省略不可靠特征，保留名称、动作构图，让图片模型发挥。多主体分别处理。

搜索工具额外记录单个主体名与搜索前认识，搜索完成后规划模型逐主体给出一致、冲突、无先验或搜索不可用的判断。主模型只接收判断和失败次数，全文查询才返回证据。报告冲突却没完成图片核对、搜索明确报错却声称已核实的方案不能进入待审；不会通过字符串匹配替代模型的语义判断。主聊天模型补充的角色常识不能冒充用户硬性要求。

插件记录真实搜索结果，核对只能使用本次结果中的来源；两次核对之间必须再次执行搜索，第二轮不重复比较相同图片字节。达到规划时限后允许提前结束，不再强制完成第二轮；未完成的核对不能被标记为成功。下载只允许公开 HTTP(S) 地址，并限制 DNS、重定向、大小与耗时。

搜索仅继承当前聊天请求实际启用的 AstrBot 内置联网工具（Baidu、Tavily、Bocha、Brave、Firecrawl、Exa、AnySearch 及对应页面读取工具），不新增搜索 Key，也不自动开启被禁用的工具。自定义 MCP 搜索工具暂不自动转交。没有联网工具时在摘要中标明限制，要求规划模型省略无法可靠描述的特征。

联网判断、文字是否一致及图片语义核对仍由规划模型完成。正常流程最多两轮核对，但受40秒规划预算约束。已核对特征被规划模型改写为同义表达时，插件会把核对原文作为优先约束补入提示词，避免仅因未逐字复述而重新规划。超时兜底保留已经完成的证据，未确认主体标为 `unverified`，不得把存疑外观当成确定事实；可通过全文查询查看限制。兜底收尾无法使用模型时，自动画风使用净色动画壁纸；已有画风、配置禁用和用户明确的画风要求优先。

## 图生图

直接发送或引用图片，沿用 1.3.0 的第一张可用图片解析。

- `image_mode="reference"`：以用户图片为主体依据，按委托及相容内置风格创作。仅说“参考这张图”属于这一模式。
- `image_mode="edit"`：仅局部修改，其余保持原图，不自动改变画风。
- `image_mode="auto"`：默认，由规划模型根据委托判断。

有用户图片时，规划模型通过视觉理解图片，**不获得任何搜索或三方核对工具**。提示词模型不看图。方案保留本次用户图片引用，后续确认出图不会换成另一条消息的新附件；修改同一待审稿时可以沿用原输入图。

视觉规划不可用时仍保留用户原图交给图片模型执行委托，不声称已经看图核实。明确指定的 `reference/edit` 保持不变；`auto` 在兜底时保守采用 `edit`，不自动改变原图画风。

## 后续修改与缓存

普通修改可直接调用 `prepare_drawing(brief="只改指定部分", use_last=true)`，插件将同一会话、同一用户最近的完整提示词直接交给规划模型。主聊天模型无需先读取或复述全文。

`get_last_image_prompt()` 默认仅返回摘要和编号；需要检查实际执行文本时使用 `full=true`。完整画风与全局兜底段沿用时不重复叠加，换风格时规划模型应移除旧风格段。

方案与证据缓存最多 100 份、30 分钟，估算体积上限 128 MiB；最近执行提示词最多保留 100 个会话/用户记录。缓存均在内存，重启后清空。历史提示词用于延续内容，不保存成图像素；精确修改某张成图时可引用该图片消息。

`accepted` 仅代表后台任务已提交，此时提示词可能仍在整合，不代表已开始生成图片或已经成功。完整提示词就绪时才更新最近执行记录。审核拒绝后的安全替代提示词会更新方案全文与最近记录，并标记原摘要可能已不准确，主模型可按需查看实际文本。

排查日志可按 `plan_id` 与 `umo` 串起 `plan ready`、`accepted`、`prompt ready`、`generation request` 和 `delivered`：分别对应待审、后台受理、风格选择、实际图片请求全文和平台推送结果。`get_drawing_plan(full=true)` / `get_last_image_prompt(full=true)` 同时提供 `style_selection`；若发生安全改写，该字段代表最初整合时的风格选择，实际执行文本以最新 `prompt` 为准。`delivery_failed` 表示平台未接受发送，不记作成功。

## 配置与保留行为

新增 **绘图规划模型 `planning_provider_id`**，可选择独立的 Provider，需要工具调用与视觉能力。留空时复用当前聊天 Provider，仍运行在独立上下文，不带入聊天历史。

`rewrite_provider_ids` 继续用于提示词整合、关键词优化及审核后的安全改写，不负责规划或图片核对。建议为规划模型选择有足够推理、工具调用和视觉能力的模型，整合模型只需可靠遵循文本与 JSON 指令。

其余配置和 13 个内置风格保持原有体系。`style_mode` 为 `auto` 时自动选相容风格，`explicit_only` 只在点名时使用，`disabled` 关闭；后两项也适用于参考图。`style_strength` 控制片段使用程度。

关键词 `triggers` 的匹配、去重、同步出图和提示词优化保持 1.3.0 路径，绕过新增规划与审核入口。Modelink API、PNG 输出、并发、网络重试和上游实际审核拒绝后的五级安全回退保持原有行为。

## 验证

```shell
python -m unittest discover -s tests -v
```

离线测试模拟 AstrBot Provider、工具执行、图片下载和出图接口，覆盖独立规划、审核入口、真实搜索记录、两轮核对、图生图隔离、按需全文、缓存继承、用户隔离、重复出图与关键词路径。实际模型的规划质量、摘要忠实度与成图效果需在 AstrBot 中联调。
