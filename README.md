# astrbot_plugin_qiniu_image

七牛 Modelink 原厂 `bypass` 协议绘图 / 改图插件，适用于 AstrBot。

## 使用

直接用自然语言请求绘图或改图，例如：

```text
帮我画一只穿宇航服的柴犬
把这张图改成夜景
```

插件默认通过 `draw_image` 工具触发，由主聊天模型理解完整上下文和 Bot 人设；也可通过 `triggers` 配置确定性的直接出图触发词。改图或参考人物时可直接发送图片或引用图片消息，主聊天模型通过结构化任务明确图片用途。

## 内置风格

插件会在同一次提示词改写中，根据用户需求选择一个合适的内置风格或借用其部分特征；只有风格与需求明显冲突时才不选择。用户明确指定的内容和风格始终优先，不会为了套模板而替换角色、品牌、文案、构图或配色。改图时只有用户明确要求风格化，才会改变原图画风。

当前内置风格：

- 净色动画壁纸
- 文艺电商联动物料
- 俄国构成主义
- 错位矩形·强故障版
- 错位矩形·诗意窗口版
- 混合媒介·照片与素描
- 半调双色雕刻
- 半调杂志
- 波普与水墨喷溅
- 克莱因秩序
- 米白红色电路图
- Y2K 与波普艺术
- 赛璐璐平涂与思维爆发

自动选择会优先考虑：净色动画壁纸、两种错位矩形风格、半调杂志、波普与水墨喷溅、米白红色电路图、赛璐璐平涂与思维爆发。

插件还注册了 `list_image_styles` 查询工具。普通聊天中用户询问“你会哪些画风”或要求推荐风格时，聊天模型可以直接读取与实际预设同源的风格目录，无需维护一份容易过期的独立 Skill。

主聊天模型结合人设、完整群聊上下文和必要考据完成创作，再提交完整方案及结构化 `task`。任务分开记录用户明确要求、本轮改动、保留项、有来源的人物资料和模型自行选择的内容，优先级按此顺序执行。优化模型只整理、核对并应用风格规则，不重新解释整段群聊。多人任务使用整体构图和逐人描述，并校验人物数量、标识、顺序及参考图绑定。关键词直出仍把触发词后的文本作为完整方案。

调用 `draw_image` 时，聊天模型应直接识别常见作品、角色和昵称，并补全关键官方信息；知识不足以可靠还原或无法唯一识别主体时使用 Web 搜索，并且必须先等待搜索结果，再调用绘图工具。搜索和绘图不能并行。这个限制通过工具说明引导聊天模型执行，插件本身无法拦截 AstrBot 对其他工具的调度。

插件在聊天请求前提供风格名称与别名，以及当前会话中当前用户最近 3 条成功作品的摘要，不替换 Bot 人设或复制整段历史。例如“错位千束”会先按内置风格理解，再决定是否需要搜索人物。风格目录工具只输出标题。

每次绘图返回 `generation_id` 和后台受理状态，完成后自动发送图片。作品记录按“会话＋发起用户”隔离，包含实际执行稿、人物资料、成图和参考附件。任务传入 `base_generation_id` 即可直接继承，无需额外调用查询工具；`latest` 只指当前用户最近的成功作品。`get_last_image_prompt(generation_id="latest")` 仍可读取指定作品的完整执行稿和人物摘要。指定作品不存在、已过期或属于其他用户时不会悄悄改为新画。

作品及参考图片保存在插件专属系统临时目录，元数据仅在内存中。缓存合计最多 100 条、512 MiB；30 分钟后不可读取，每分钟清理过期文件，超限先淘汰最旧记录，卸载时清理。每份作品保存参考图副本并计入容量，避免原参考图先过期影响后续编辑。后台启动前固定基础作品和缓存引用，其他请求完成不会改变其目标。插件重启后不恢复这些记录。

优化时 `anime style`、`masterpiece`、`highly detailed` 等泛化质量词不会被误判为完整画风。内置全局审美规则会在所有普通优化中注入，进一步约束动画画面使用大色块、低视觉频率、受控边缘密度、清晰边缘层级、少量内部轮廓线和大块阴影，并抑制碎阴影、微纹理、微对比和无必要高光。

内置风格名称只用于路由和日志，不会发送给图片模型。插件会删除内部风格标记、中文风格名及别名，只保留展开后的构图、色彩、线条和材质描述。日系动漫、漫画及游戏角色默认使用官方日文作品名、角色名和画内字样，不使用中文译名作为海报装饰文字。

风格优先级依次为：用户本轮明确指定的画风；目标作品需要保留的原有画风；主模型自行选择的画风。图片不作为画风依据。`auto` 模式下，主模型先从相容的内置高偏好风格中选一个，优化器也按此规则核对；自行补上的普通动画主视觉、电影感或 3D 渲染不视为用户指定画风，人物原作品为 3D 也不锁定本次媒介。用户指定外部画风、原风格复刻或局部编辑保留原貌时仍优先遵守。旧工具调用和直接触发词没有结构化来源信息，继续尊重完整提示词中的具体画风。`explicit_only` 仅响应用户点名，`disabled` 关闭内置风格路由；`style_strength` 控制表现强度。

优化器启用风格路由时必须返回一个有效的内部风格选择标记（允许明确选择不使用），缺失或无效时按原有优化 Provider 重试、回退。线条执行约束同时发送给优化器和绘图接口，减少草稿复线、乱排线、密集碎发及装饰线；错位、思维爆发和电路等预设也减少线网及碎片。人物标志物、明确要求的线性艺术和局部编辑保留项优先，不一律删除必要细节。

提示词优化与全局审美规则为固定流程。人物参考图仍通过 AstrBot 的 `image_urls` 提供给优化模型，用于核对身份和稳定外观特征；优化模型不得从图中继承动作、镜头、构图、背景、光照、材质或画风。只有原消息存在 `input:N` 图片绑定时，图片才会实际传给七牛绘图接口；原消息无图时最终走纯文字生成。主聊天模型继续负责会话和人设理解，优化模型只接收本次任务和目标作品相关资料。

## 结构化任务与人物参考

`draw_image(prompt, task=None)` 保留旧调用；不传 `task` 时继续采用有输入图则编辑的行为。传入任务后必须明确 `operation`：

| 字段 | 说明 |
| --- | --- |
| `operation` | `create` 新画、`edit` 局部编辑、`redraw` 整张重画 |
| `base_generation_id` | 要继承的作品标识或 `latest`，新画省略 |
| `user_requirements` / `changes` | 用户本轮明确要求与具体改动，字符串数组 |
| `preserve` / `creative_choices` | 保留项与主模型自行选择的创作细节，字符串数组 |
| `characters` | 逐人人物资料；局部编辑按稳定 `id` 合并补丁，保留其他人物 |
| `character_count` | 可选，必须与合并后的实际人物列表一致 |
| `image_roles` | 图片用途列表；显式提供时替换继承的图片用途，人物条目中的参考仍参与绑定 |

人物条目使用 `id`、`name`、`work`、`version`、`position`、`features`、`evidence`、`identity_status` 和可选 `reference_id`。新人物需要关键外观；已知人物使用 `confirmed` 并提供依据，原创人物使用 `original`，`uncertain` 会停止生成。多人必须逐人指定观看者视角的位置。`edit` 不能改变已记录的人物身份或新增人物，需要改变名单时使用 `redraw`。

人物指代优先沿用当前会话、用户确认与目标作品的可靠资料，近期摘要补充身份依据。身份已知但外观不清时，用准确姓名和作品／身份定向查外观；未知昵称先形成候选并核实别名关系，不预先限定动漫或游戏类别。搜索已出现昵称与准确姓名关联时继续核实该线索；历史查询为空不推翻已有确认。这些是主模型的理解规则，不建立“小秦”等昵称的全局固定映射，也不新增补图追问或等待任务。

图片用途条目为 `source`、`role` 和人物参考所需的 `character_id`。`source` 可为 `input:1` 等本条／引用图片序号或参考工具返回的标识；`role` 为 `character`、`style` 或 `edit`，其中 `style` 仅为兼容保留，不读取画风。每个人最多绑定一张人物参考，支持五人分别绑定五张；编辑需要且只能有一张编辑原图。人物参考图只提供给主模型／优化模型用于核对身份和稳定外观特征，不得用于动作、镜头、构图、背景、光照或画风；这些内容必须来自文字方案。用户原消息没有 `input:N` 图片时，最终图片模型不接收任何参考图，走纯文字生成。用户明确换装、动作或风格优先于参考原貌。

例如，修改之前作品中的花音，保留其他人：

```json
{
  "prompt": "修正花音的黄色蝴蝶结，其余人物和构图保持原样",
  "task": {
    "operation": "edit",
    "base_generation_id": "gen_实际作品标识",
    "changes": ["只修正花音的黄色蝴蝶结"],
    "preserve": ["其他四个人的外观、位置和构图"],
    "characters": [{"id": "kanon", "name": "中川花音", "features": ["粉色短发", "脑后的大黄色蝴蝶结"]}]
  }
}
```

此例假定基础作品已记录 `kanon` 及完整人物资料。编辑使用已有成图，不只继承文字；普通图像编辑仍可能改变其他区域，此版本不提供蒙版合成或像素不变保证。

`prepare_character_reference(subject, source_urls, evidence)` 使用 Tavily 已返回的网页地址，不修改内置搜索、不增加搜索 API Key。主模型先消歧，再提交准确人物、版本、1～3 个页面或图片地址及依据。插件提取正文／懒加载／封面候选，最多尝试读取 6 张，沿现有模型列表核对后选 1 张，返回 `canonical_name`、外观摘要、来源和 `reference_id`。人物条目名称需与工具返回的准确名称匹配。

用户主动提供的图片也可在 `source_urls` 中以 `input:1` 等标识提交，经过同一轮视觉核对后生成参考标识，无需向用户追问。显式任务只读取绑定的输入图片；未绑定的聊天图片不影响新画或已有作品编辑。冲突的人物参考用途不会被静默忽略。自动选中的内置画风会写入作品摘要，供后续继承。

网页取图只访问公开 HTTP(S) 地址，检查 DNS 和每次重定向，拒绝内网、凭据 URL、异常端口、过大内容与不支持的格式。取图总预算 40 秒，单个候选读取最多 10 秒；不会绕过登录或反爬。来源不可用或核对不确定时不使用候选图；只有身份外观已有充分文字依据时才继续文字生成。人物依据不足则结束，不询问补图、不等待回复。

## 多人出图检查

多人图生成后，沿现有优化 Provider 配置执行一轮视觉检查；每个 Provider 最多尝试一次。检查人数、位置、关键外观和特征串位，局部纠错还对照原图检查其他人物是否明显变化。发现问题会随图片简短提示；检查失败仍发送已经生成的图片并说明未完成核对。检查不会自动修图或重新生成。

图片核对、人物参考优化与多人检查需要视觉模型。插件不会在视觉调用异常时静默丢图重试；有充分文字依据且仅使用人物参考的新画可以明确降级为文字生成。编辑原图无法读取时终止该请求。视觉检查不能保证发现所有错误，也不能保证完全复刻人物。

## 安全转译

首次出图前不进行风险词检测，也不注入安全转译规则。只有图片平台实际返回安全审核拒绝后，插件才会生成安全替代提示词并继续尝试，固定最多 5 级。安全程度逐级递进：先通过同义替换、隐晦措辞等措辞级调整尝试保留原画面（不改动服装、场景、姿势与构图），前两级还会优先使用动画角色插画、角色立绘、轻小说封面、动画剧照等二次元插画语境措辞，并避免私密场景、暴露服装与挑逗姿势叠加；仍被拒绝后才依次增加遮盖并减弱暗示、改为完整家居服或时装、端庄日常服装与中性场景，最后才是全年龄普通角色插画。某一级的安全改写模型若拒绝回答、返回空内容或无效结果，插件不会立即终止，而会继续尝试更保守的下一级；图片平台再次拒绝时同样推进一级。全部级别都无法产出可用图片后才失败。它不会原样生成裸露、性行为或未成年人性化内容。`moderation` 默认 `low`（放宽审核阈值，仅对中等敏感内容有效），如遇上游不支持该参数或需要更严审核，可设为 `auto` 恢复上游默认。

`rewrite_provider_ids` 使用 AstrBot 的有序模型选择器：第一项是主优化模型，后续项按顺序作为回退模型；留空则跟随当前会话。每个模型固定最多调用 3 次。全部优化模型均失败时，本次绘图会终止，不会把未经优化的方案直接发给图片模型。该选择器在 AstrBot v4.28.0 可用，目前属于 AstrBot 内部配置控件，未来大版本若调整内部接口可能需要随之适配。

图片请求遇到网络异常、限流、5xx 或异常响应时固定最多尝试 4 次，单次请求总超时为 480 秒；鉴权、权限和参数错误不会进行无意义重试。纯文字绘图可以使用文本优化模型；使用参考图、改图和多人检查时应配置支持图片输入的模型。

## 配置

配置页面保留 API Key、图像模型、提示词优化模型、画质、尺寸、审核严格度、并发数、风格模式、风格强度和可选直接触发词。默认模型为 `openai/gpt-image-2.5-sunburst`，默认并发数为 3。插件固定使用官方 API 和 PNG 输出；主模型工具调用采用后台出图，关键词直出同步返回结果，并使用具有冗余的超时、重试和安全回退。改图输入支持 PNG、JPEG、WebP、GIF，单张本地输入按 Modelink 文档限制为 40 MB；输出接收上限为 80 MiB，为 4K PNG 留出余量。

## 开发验证

运行 `python -m unittest discover -s tests -v`。离线测试模拟 AstrBot 事件、模型及网络，覆盖任务继承、人物绑定、请求图片顺序、Provider 回退和网页读取限制，不调用真实绘图服务。

接口依据 AstrBot v4.28.0 的 `on_llm_request`、`ToolSet` 和 `Context.llm_generate(image_urls=...)`；工具 schema 在请求时显式补全嵌套对象。实际部署还应检查工具可见性、配置模型的视觉能力和七牛多图响应，并用日志中的五人组合与参考图人工对照效果。
